# Recovery calibration: independent source audit

## Conclusion

The primary judgments are supported by the inspected source: K001 has no established necessary correction under the supplied contract, and K003 requires the correction retained as A_F1. The two K003 critic findings describe one cause, and the adjudicator correctly retained A_F1 and marked B_F1 as its duplicate. The counterexample, business impact, and minimal correction are sound. No additional independent implementation defect was established.

There is a narrower reporting limitation: K003's unconditional C5 `supported` assessment overstates the provenance guarantee for repository aborts after the already identified classification defect. The same defect can also contaminate the prior-refusal list of a deferred decision. These are effects of A_F1, not additional necessary changes or additional defects. The original review JSON was not changed.

## Evidence and method

I read the complete before and after production source, the actual change diff, API.md, CHANGE.md, RUBRIC.md, IMPLEMENTATION.md, both final.json documents, both combined.json documents, and the frozen recovery control metadata. Both packages contain one production source file per side. Their before sources and contracts are identical. Their after sources differ only at line 227. K001's after source is byte-identical to the frozen reference source; K003's is byte-identical to the frozen broken source. The displayed AFTER.md and DIFF.patch differences reproduce that same change.

Those comparisons establish which artifacts were reviewed; they are not a correctness grader. The conclusions below follow from contract clauses and source paths. The frozen control's expected labels and its list of non-defects were treated as claims to check, not as an oracle. No implementation, tests, or additional assessment model was run. No protocol or review output was edited.

Unless stated otherwise, source citations below are relative to `calibration/<candidate>/package/`. Line numbers in the two after sources are identical.

## K003: the retained finding is valid and singular

The changed classifier fallthrough at `after/src/index.ts:227` returns `{ kind: "refused", reason: "unsupported_route" }` for unrecognized rejected values. `attempt` catches a carrier rejection at `276–277` and invokes this classifier. The resulting `refused` branch at `373–377` records the invented refusal and calls Beacon. The otherwise correct unknown-abort branch at `384–385` cannot receive this outcome.

A complete permitted counterexample is a queued record `{schemaVersion:1,id:"shipment-1",routeCode:"ZONE-N",parcelGrams:500,state:"queued"}` and a dispatch with nowMs 1000 and nonblank recipient fields. The repository read resolves that record. Atlas rejects an Error with no documented signal fields. Beacon, if called, confirms `{reference:"beacon-1"}`; save resolves and the logger records events. The actual path calls Beacon, saves a dispatched Beacon record, emits `dispatched`, and returns 200. CHANGE.md:25,37,45,66 instead requires Atlas-only execution, no write, a 500 Atlas `unknown_failure` with `rejections:[]`, and one abort event. A genuine Atlas refusal followed by an unknown Beacon rejection similarly commits a fabricated unavailable decision rather than preserving only the genuine Atlas context in an abort.

The impact description is justified. CHANGE.md:66 explicitly allows an unknown failure after carrier acceptance and disclaims cross-carrier idempotency. The unnecessary Beacon call can therefore create another booking. The audit does not claim that every Error implies an existing Atlas booking, or that rollback/compensation is required.

The smallest correction is the single fallthrough replacement at line 227 with `{ kind: "unknown" }`. No other branch needs to change: valid documented refusals, future throttles, malformed known signals, confirmation validation, and the contextual abort path already exist. This restores both carriers' unknown-failure behavior. Regression obligations should preserve those neighboring paths, save-before-event order, and the selected public fields.

`calibration/K003/final.json:341–386` retains this cause once; `515–550` accepts A_F1 and merges B_F1 into it. C1, C4, and C6 are legitimate affected obligations, even though the frozen control metadata lists only C4 and C1. The extra C6 mapping is supported by the wrong event on the same counterexample, not by a second defect. Both critics' source evidence and the adjudicator's retained claim agree on the cause. K001's combined and final reviews contain no findings; K003's combination contains two proposals and its final contains one retained finding.

## Requirement-profile limitation: the same cause reaches additional context fields

**C5 overstatement.** `calibration/K003/final.json:247–277` marks C5 supported and says save failures carry established refusals. Extend the preceding permitted counterexample so Beacon confirms but repository.save rejects. The invented Atlas refusal is appended at `after/src/index.ts:374`, passed to the booked commit at `358–364`, and copied into the repository abort response/event through `289–294` and `231–253`. The actual response has `failedAt:"repository"`, `classification:"repository_failure"`, and an Atlas `unsupported_route` refusal that was never established. In the contractually correct execution Atlas's unknown failure aborts first, so Beacon and save are never reached. Even the observed repository-abort context fails C5's explicit established-refusals requirement (CHANGE.md:41).

The repository catch and save ordering themselves are correct. With a genuine Atlas refusal followed by Beacon confirmation and save rejection, the context is correct. The limitation is specifically the earlier fabricated provenance flowing into that otherwise correct boundary. Restoring line 227 removes the path; it is not a second repository implementation correction.

**Related deferred-context consequence.** If the unauthorized Beacon attempt instead rejects a valid throttle `{type:"throttled",details:{retryAtMs:1700}}`, `after/src/index.ts:365–372` saves a Beacon plan with that same invented Atlas refusal, and `304–312` emits it. Deadline validation and durable resumption still work, but the resulting prior-refusal provenance is not established. K003's C2 supported rationale at `final.json:161–184` should not be read as an unconditional guarantee that all emitted plans have genuine prior refusals. The correct invocation again aborts at Atlas. This is another effect of A_F1, not a new rate-limit defect.

Accordingly, the primary outcome and one-cause correction count are reliable for this pair. An unqualified count of supported requirement rows would hide these propagated effects. Preserve this supplement when interpreting the requirement profile; do not convert each affected requirement or execution path into an additional defect. The original evidence already supports the necessary single correction without changing the frozen expected labels or adjudication JSON.

## Scope limits

No finding is based on absent validation of arbitrary corrupt storage, logger exceptions, concurrency, process crashes, compensation after a rejected save, changing recipients, wall-clock time, strict postal syntax, or DLP over contractually non-PII identifiers. These are excluded or unnecessary under API.md and CHANGE.md:144–150. A later explicit dispatch after abort/save failure can reuse the carrier's stable key; the contract does not require preservation of refusals that were never successfully saved. No points or findings were assigned for libraries, file organization, type style, or the number of edits.
