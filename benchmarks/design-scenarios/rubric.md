# DMMF設計手法の適用評価 — 判定基準ドラフト

版：0.1。状態：レビュー用・未校正。採点器と校正用の実装対照は未作成。

## 1. 評価するもの

**同じPRDに対して生成されたコードに、Domain Modeling Made Functional（DMMF）の設計手法が、どこまで実質的に適用されているか。**

機能要件を満たすことは課題の前提であり、ここで測る能力にはしない。機能テストの得点、通過数、合否ゲート、不具合件数、機能適合性の別審査を、この評価に持ち込まない。設計上の不足を指摘するために、外部APIの不具合を立証する必要もない。

PRDは、ドメインの概念、状態、制約、業務の流れを読み取る材料にする。その意味が型と関数の設計にどう表現されているかを判定する。設計書の宣言だけで判定せず、実際に使われるコードまで追う。

この基準はDMMFの適用を測るものであり、あらゆる設計流派に共通する品質点ではない。「この手法を使っていない」と「機能に不具合がある」は別の判断である。総合的な優劣や保守工数の差を、この適用評定から直接導かない。

DMMFの全領域を一度に採点するものでもない。PRDを与えてコードを生成させる実験では、ドメイン専門家への聞き取りや組織の分割過程そのものは観測できない。最初のドラフトは、生成コードと実際の後続変更から観測できる7軸に絞る。

## 2. 判定単位と共通尺度

### 判定単位

単位は、**評価軸 × 事前に指定したドメイン概念・処理経路**とする。たとえば「D2：経費の支払済み状態と、その状態を作る遷移」が1単位になる。

課題を作る時点で、評価側が次を固定する。生成側には、この評価用の指定を渡さない。

| 指定項目 | 例 |
| --- | --- |
| ドメイン上の意味 | 支払済みの経費は、確定した受領番号を持つ |
| 評価する設計手法 | 状態別の型と、遷移元・遷移先を表す関数契約 |
| 追う範囲 | 状態型、生成・復元経路、支払後の遷移、内部の利用側 |
| 確認する設計上の問い | 受領番号がない支払済みの値を、通常の型付きコードで作れるか |
| 今回は評価しないこと | 支払いAPIの成功率、決済ゲートウェイの応答速度 |

実装を見る前に範囲を決める。気に入った箇所だけを選んで高評価にしたり、不利な箇所を後から対象外にしたりしない。全候補の同じ単位を比較する。

### 共通尺度

| 評定 | 意味 | 必要な根拠 |
| --- | --- | --- |
| 0：未適用 | 対象の処理はあるが、評価する設計手法が使われていない | 実際の表現と処理を示し、何を手作業や実行時の分岐に委ねているか説明する |
| 1：形式的適用 | 名前・型・部品はあるが、対象の処理に設計上の制約を与えていない | 宣言と実際の利用の断絶、または制約を持たない表現を示す |
| 2：部分適用 | 実際の処理の一部では成立するが、指定した範囲内に適用の途切れがある | 成立する経路と、型情報の消失・迂回・別表現への退行を両方示す |
| 3：一貫した適用 | 指定した範囲で、宣言・構築・変換・利用が手法の意図を保っている | 主要な経路を追い、成立の仕組みと、検討した反証を示す |
| U：未確定 | 対象のコードや証拠が不足し、評定を確定できない | 不足する資料、読めていない経路、未解決の論点を明記する |
| N/A：対象外 | 課題に、その手法を使う機会がない | 課題設計時に固定した対象外の理由を示す |

0〜3は順序を表す。隣接する段階の差が同じ大きさであるとは仮定しない。初版では平均、重み付き総合点、単一順位を出さない。

1と2の境目は、実際の業務処理に制約を与えている箇所があるか。使われない型を宣言しただけなら1。実際の段階では型が働き、その後の段階で失われるなら2。

処理自体が未実装・資料欠落なら、0にも3にもせずUにする。対象機能を省いたことをN/Aの理由にしない。3も「問題を思いつかなかった」だけでは成立しない。

## 3. 7つの評価軸

### D1：ドメイン概念を型で表す

**問い：** 業務上異なる値、識別子、単位、概念の関係が、利用側に意味のある型として現れているか。

観察するもの：概念の型、値の生成方法、関数の引数・戻り値、実際の受け渡し。課題に現れる場合は、値の同一性とエンティティの識別、集約のまとまり、異なる文脈の概念の区別も見る。

| 評定 | 判定例 |
| --- | --- |
| 0 | 区別が必要な従業員IDと経費IDを、どちらも無制約の文字列として受け渡す |
| 1 | `type EmployeeId = string`のように名前を付けたが、経費IDをそのまま渡せる。制約のある型を定義していても、業務処理が使わない |
| 2 | 検証済みの金額やIDを使う経路がある一方、指定した別の内部経路では通常の数値や文字列に広げている |
| 3 | 対象の概念が意味に応じて区別され、値の生成から内部の利用までその区別が保たれる。混同できない理由を型と受け渡しから説明できる |

ブランド型の個数では判定しない。ラッパー、非公開の構築、識別可能な構造など、TypeScript上で同じ意図を実現する方法を認める。意味の区別が不要なすべての文字列に専用型を要求しない。

### D2：不正な状態を表現できなくし、遷移を型で表す

**問い：** 状態ごとの必要情報と、どの状態からどの状態へ進めるかが、型と遷移関数の契約に表れているか。

観察するもの：状態の型、必須情報、構築・復元経路、遷移関数、呼び出し前の絞り込み、内部の利用側。

| 評定 | 判定例 |
| --- | --- |
| 0 | 単一の経費型に状態名と任意の受領番号があり、必要情報を各処理の分岐だけで確認する |
| 1 | 状態別のunionはあるが、支払済みでも受領番号が任意。または厳密な状態型が実処理から使われない |
| 2 | 支払済み型では受領番号を必須にしているが、指定した内部経路の一部で広い型に戻したり、状態を任意に変更したりできる |
| 3 | 状態ごとの必須情報が表現され、遷移契約が有効な元状態と先状態を示す。実際の呼び出しと復元経路も、その制約を保っている |

外部コマンドを受ける入口まで`ApprovedExpense`を要求しない。入口で状態を確認し、絞り込んだ値を型付きの遷移関数へ渡す構成も3になり得る。

「元状態が承認済み」と「承認者が申請者と異なる」は別の制約である。動的な値同士の関係を、根拠なく型で保証済みと扱わない。どの制約を型で表し、どれを明示的な判断に残したかを記録する。

### D3：外部表現を検証し、ドメインモデルへ変換する

**問い：** 外部のデータ形式と内部のドメインモデルの間に、検証と変換の明確な境界があるか。

観察するもの：入力の型、DTO、パーサー、検証結果、ドメインへの変換、保存データからの復元、内部への受け渡し。対象となる外部境界は事前に列挙する。

| 評定 | 判定例 |
| --- | --- |
| 0 | 外部値を型注釈や`as Domain`で内部の値として扱い、型付きの変換境界がない |
| 1 | スキーマや変換関数は宣言したが、検証した値ではなく元の外部値を実処理に渡している |
| 2 | API入力では検証結果からドメイン値を作るが、対象に含めた保存データの復元では無検証のキャストを使うなど、一部の境界で途切れる |
| 3 | 指定した外部境界が、検証と変換を通じて内部モデルへ接続する。DTOの都合が内部の判断へ漏れず、検証結果を利用していることを追える |

Zodなど特定のライブラリの使用は条件にしない。手書きのパーサーも、その出力と利用の仕方で判定する。外部との通信形式が文字列や数値であること自体は減点しない。

検証ルールの網羅テストを作る軸ではない。「不正メールを拒否するか」ではなく、「外部の文字列から、内部が信頼するメールの値へどのように移るか」を見る。

### D4：ワークフローを型付きの変換として構成する

**問い：** 業務の段階が意味のある入力・出力を持ち、その接続によってワークフローを読めるか。

観察するもの：コマンド、各段階の契約、中間値、段階の接続、最終的なドメイン上の結果。課題で意味を持つ場合は、結果を出来事として表すイベントと、その利用側も見る。

| 評定 | 判定例 |
| --- | --- |
| 0 | 汎用の入力オブジェクトからHTTP応答までを処理し、業務の段階に対応する契約がない |
| 1 | `validate`、`price`などに分割したが、全段階が同じ無制約のデータ袋を受け渡し、進行による意味の変化を表していない |
| 2 | 検証済み・価格計算済みなどの段階型が実際に使われるが、途中で汎用オブジェクトへ広げたり、未処理の値を後段へ渡せる経路が残る |
| 3 | 各段階の契約と接続から、前提、変換結果、進行が読める。実際の経路でも、前段が作った意味のある値を後段が受け取る |

専用のパイプ演算子、関数合成ライブラリ、特定のファイル分割は要求しない。通常の関数呼び出しや逐次的な束縛でも、意味のある段階と型の接続があればよい。段階を増やすためだけの中間型や細分化は加点しない。

### D5：純粋な業務判断と副作用を分離する

**問い：** 業務判断が明示された値に基づく変換として成立し、I/Oや非決定性の扱いを接続部分から追えるか。

観察するもの：判断関数、入力値、戻り値、参照の変更、DB・外部API・時計・乱数へのアクセス、依存を接続する場所。

| 評定 | 判定例 |
| --- | --- |
| 0 | 判断の内部でDBや時計を直接参照し、隠れた状態や副作用と業務ルールが一体になっている |
| 1 | 依存を引数に移したが、業務判断そのものがリポジトリなどを呼び続け、値だけで表せる判断を分離していない |
| 2 | 主要な判断は純粋だが、対象の別経路で現在時刻を直接取得する、入力の共有状態を書き換えるなど、分離が途切れる |
| 3 | 対象の判断を明示的な値からの変換として追える。副作用は接続部分にあり、実際の判断経路で隠れたI/Oや状態変更に依存していない |

必要な外部照会が業務の途中にあることを一律に減点しない。照会を行い、その結果を次の純粋な判断へ渡す構成も成立する。すべてのI/Oを開始前に済ませる設計は要求しない。

`readonly`という語だけから実行時の不変性を主張しない。入力から結果までの実際の更新と参照を読む。あらゆるオブジェクトの凍結や、外部の任意の悪意ある変更への防御は要求しない。

### D6：業務上の失敗を明示し、合成時に意味を保つ

**問い：** 業務上の失敗の種類と必要な情報が型に表れ、それを扱う処理まで維持されているか。

観察するもの：成功・失敗の型、失敗を作る場所、変換・合成、回復判断、最後に業務エラーを扱う関数。

| 評定 | 判定例 |
| --- | --- |
| 0 | 想定する業務上の失敗を文字列や例外の暗黙的な取り決めで扱い、呼び出し契約に選択肢が表れない |
| 1 | `Result<T, Error>`や無制約のタグを導入したが、業務上の失敗の選択肢と必要情報を表していない |
| 2 | 用途に応じたエラーunionが実処理で使われるが、共通ハンドラーで`kind: string`に広げる、回復に必要な情報を途中で落とすなどの途切れがある |
| 3 | 業務上の失敗が区別され、合成・変換を経ても、判断する側に必要な選択肢と情報が届く。最終的な業務エラー処理まで型の対応関係を追える |

すべての障害をResultへ入れることは要求しない。業務として回復判断する失敗と、それ以外の実行障害を区別する。特定のライブラリや、すべての例外を一律に禁止する規則にはしない。

最後にHTTP応答へ変換して文字列を返すことは、型情報の不適切な消失とは限らない。**業務上の選択肢を判断する前に**型を広げているのか、閉じた選択肢を扱い終えた後で外部表現へ変換しているのかを区別する。

### D7：後続変更でも設計手法を維持・発展させる

**問い：** 実際の要件変更で、型、ワークフロー、判断の分離を更新し、設計手法を保った実装にできるか。

初期実装だけから将来の変更容易性を推測しない。初期実装を固定した後、事前に決めた変更を各候補自身のコードへ実装させる。変更前後のコードと差分を評価する。

| 評定 | 判定例 |
| --- | --- |
| 0 | 対象の変更を、無制約のフラグや各呼び出し元の個別分岐で処理し、評価する設計手法を用いていない |
| 1 | 新しい型や段階を追加したが、実際の変更経路では使われず、設計の説明だけが更新される |
| 2 | 一部は型や段階に反映したが、別の利用側では型を広げたり、同じ業務ルールを個別に複製したりして適用が途切れる |
| 3 | 変更をモデル・段階・依存の接続へ反映し、影響を受ける実際の利用側まで制約を保つ。必要な再設計も含め、判断やルールの所在を追える |

変更例は、新しい必須情報を持つ状態、検証後に追加される業務段階、新しい業務エラーなど。選択した変更がどの設計手法を観察する機会になるか、生成前に記録する。

変更ファイル数、行数、所要時間をこの軸の評定に使わない。元の構造を保持すること自体にも加点しない。適切な再設計によって適用が改善した場合も、変更前後の違いとして記録する。

実際の変更がない場合、この軸はU。コンパイラが修正箇所を示したと主張する場合は、その具体的な型関係や記録を示し、想像で補わない。

## 4. 重複と例外の扱い

- **宣言から利用まで追う。** `PaidExpense`という型名だけではD2を確定しない。どこで作り、どの型で渡し、どこで使うかを確認する。
- **同じ原因を別の欠陥として水増ししない。** 外部値への無検証キャストがD1とD3に影響するなら、根拠に同じIDを付けて関係を示す。軸ごとの問いには答えるが、件数を得点に変えない。
- **責任を置いた場所を読む。** 状態の判定を入口で行い、純粋な遷移に絞り込んだ値を渡す構成を「遷移内にチェックがない」という理由で下げない。
- **通常の型付きコードを対象にする。** 提出コード中の`any`やキャストによる迂回は追う。存在しない利用者が任意のキャストを書く可能性だけで、あらゆる型の保証を否定しない。
- **正当な別表現を認める。** 同じ手法の意図が成立するなら、ライブラリ名、タグ名、クラスか型か、配置の違いだけで評定を変えない。
- **kamae固有の慣習を混ぜない。** `kind`への統一、Companion Object、1概念1ファイル、特定のResultライブラリ、`Sensitive<T>`の採用は、このDMMF評定の必須条件にしない。必要なら別の評価目的として扱う。

## 5. 1件の判定記録

各判定は次の形で残す。説明の巧さではなく、第三者が同じコードを辿れることを重視する。

| 項目 | 記録内容 |
| --- | --- |
| 候補・軸・単位 | 匿名候補ID、D1〜D7、事前指定した対象 |
| 対象の意味 | どのドメイン概念・状態・段階について判定するか |
| 手法の成立条件 | 型と処理に何が表れていれば成立するか |
| 宣言・構築の証拠 | ファイルと行、型・生成・変換の仕組み |
| 利用の証拠 | 実際の呼び出しと後続処理、情報が維持される範囲 |
| 反証の検討 | 型の拡大、迂回、例外的な経路と、それへの判断 |
| 評定と理由 | 0・1・2・3・U・N/A。該当する基準を説明する |
| 判定を変える証拠 | 何が見つかれば評定が変わるか |
| 関連する根拠ID | 他の軸と原因を共有する場合の参照 |

例：支払済み型で受領番号が必須、承認済み型からの遷移があり、支払い処理が検証した受領番号を渡しているなら、D2の成立を支える。一方で別の復元経路が広い型へキャストしていれば、その経路を含む単位は2になる。名前や宣言だけを見て3にしない。

## 6. 採点器を作る前の校正案

同じ業務の実装として用意したコード対照を、設計上の一箇所だけ変えて比較する。以下は対照の設計案であり、実装済みの校正データではない。

| 対照 | 固定するもの | 変えるもの | 区別できるべきこと |
| --- | --- | --- | --- |
| C1：状態の表現 | 業務の処理と受領番号の確認 | 単一型の任意項目／状態別の必須項目 | 実行時チェックがあっても、型への表現は異なると判定できる |
| C2：型の実利用 | 業務処理、状態型の定義 | 型が未使用／実際の遷移と利用側まで接続 | 型が宣言されているだけの1と、成立する3を区別できる |
| C3：エラーの接続 | 発生する業務エラーと応答への対応 | ハンドラーで型を拡大／閉じたunionを保持 | ローカルなResult導入と、一貫した適用を区別できる |
| C4：依存の分離 | 同じ入力値、業務判断、外部呼び出し | 注入したI/Oを判断内で実行／取得値を純粋な判断へ渡す | 依存注入だけと、純粋な判断の分離を区別できる |
| C5：境界の一部欠落 | API経路と内部モデル | 保存データ復元の型付き変換だけを迂回 | 一部の成功例に引かれず、指定範囲の部分適用を捉えられる |
| C6：表面的な差 | 型が持つ制約と実際の経路 | 名前、配置、同等のライブラリ表現 | 意図が同じなら同じ評定になる |

設計上の差を作るために機能不良を仕込まない。機能テストの結果を校正の正解ラベルにしない。対照の作成者は、期待する評定と、型・データの流れに基づく理由を別に記録する。

複数の評価者が、条件名と期待評定を見ずに独立して判定する。その後、次を確認する。

1. 異なる保証を持つ対照を区別できたか。
2. 表面的な変更だけの対照を同じ評定にできたか。
3. 結論の一致だけでなく、同じ成立箇所・途切れを根拠にできたか。
4. UやN/Aを、判断の難しい箇所を避けるために使っていないか。

ずれが出たら、ソースの読み違い、基準の曖昧さ、観察範囲の不一致、対照の作り方の問題を分ける。理由と修正を残し、修正した基準で同じ対照一式を判定し直す。これらを確認できるまでは、大量生成やスキルの優劣の発表に進まない。

## 7. 比較実験へ進む場合の条件

校正後に、同一PRD・同一モデル・同一設定のスキルあり／なしで比較する。生成側に共通で与える内容に、評価用の手法一覧、過去の設計書、このドラフトを含めない。baselineにkamaeの手法を先回りして指定しない。

評価側は匿名IDのコードを読み、初期実装のD1〜D6と、実際の変更を含むD7を分けて報告する。条件名を隠しても、コードの特徴から推測される可能性はあるため、完全な盲検とは主張しない。

報告は、同じ評価単位ごとの評定、根拠、分布、未確定件数を中心にする。全計画件数を残し、未生成・資料欠落を良い結果にも悪い点数にも置き換えない。設計手法の適用差が見えたかを述べ、機能テストの比較に戻らない。

過去の生成物は、区別すべき性質を考えるための探索資料にできる。既存の結果を見た後に作った基準なので、その再評価を新しい実験の検証結果と混同しない。

## 8. 出典と、このドラフト独自の判断

DMMFとの対応は、出版社の[書籍概要と目次](https://pragprog.com/titles/swdddf/domain-modeling-made-functional/)を起点にする。

| 軸 | 対応する書籍の主題 |
| --- | --- |
| D1 | Domain Modeling with Types |
| D2 | Integrity and Consistency in the Domain; Modeling Workflows as Pipelines |
| D3 | Integrity and Consistency in the Domain; Serialization |
| D4 | Modeling Workflows as Pipelines; Implementation: Composing a Pipeline |
| D5 | Implementation: Composing a Pipeline; Persistence |
| D6 | Implementation: Working with Errors |
| D7 | Evolving a Design and Keeping It Clean |

型による状態制約は著者の[Making illegal states unrepresentable](https://fsharpforfunandprofit.com/posts/designing-with-types-making-illegal-states-unrepresentable/)、副作用と依存の扱いは後年の著者記事[Six approaches to dependency injection](https://fsharpforfunandprofit.com/posts/dependencies/)も参照する。後者を書籍本文そのものの規則とは扱わない。

7軸への区分、TypeScript上の観察方法、0〜3の尺度、校正手順は、このリポジトリの評価のために提案したもの。著者による公式な採点基準ではない。

## 9. このドラフトで先に検討する点

- **軸の重なり：** D1の値の型、D2の状態型、D3の境界、D4の段階型の責任範囲を、対照で一貫して分けられるか。
- **適用範囲：** 評価単位の指定が狭すぎて形だけの適用を見逃したり、広すぎて部分適用ばかりになったりしないか。
- **段階の境目：** 1と2、2と3の判断を、コードの具体的な差に結び付けられるか。
- **手法と流儀：** 別のTypeScript表現でもDMMFの意図が成立する場合に、同じ評定を与えられるか。

この4点を対照によって確認することが、次の作業になる。現時点では、評価基準が有効だと確認できたことにはしない。
